# ADR-0016: shadcn/ui as the interactive primitive layer, under a pure-presenter domain layer

## Status

Proposed — supersedes [ADR-0013](0013-presentational-components.md)

## Context

ADR-0013 rejected component libraries "only while the primitives stay
non-interactive containers", and named its own trigger: **the first component
needing focus management, a dialog, or a listbox**. That trigger has arrived.
The screens the receipt and bill specs describe need, at minimum:

- confirmation dialogs — finalizing a receipt (`docs/specs/receipts/totals-check.md`)
  and removing a participant (`docs/specs/receipts/participants.md`);
- a searchable picker to assign items to participants
  (`docs/specs/bills/allocations.md`);
- checkbox lists and toasts on the guest pick page
  (`docs/specs/receipts/guest-picks.md`);
- editable tables, form fields with error messages, and a user menu.

Hand-rolling the ARIA, focus trapping, roving tab index, and escape handling
for each of those is the outcome ADR-0013 said to avoid. The team's designs
are already drawn from shadcn/ui, and the frontend has one week to stand up
nine screens.

Three forces shape how the library comes in:

1. **shadcn/ui is copied source, not a runtime dependency.** Its CLI writes
   component files into the repo; the Radix packages underneath do the
   accessibility work. The copied files are ours to read, test, and change.
2. **shadcn's conventions contradict three of ADR-0013's rules**: its
   primitives take a `className` prop (merged with `tailwind-merge`), express
   variants with `class-variance-authority` (`<Button variant="outline">`),
   and the interactive ones are client components. Accepting the library
   means accepting those conventions *at the primitive layer* — fighting them
   file by file would leave us with neither shadcn nor ADR-0013.
3. **The rest of ADR-0013 still holds and is still wanted.** Components that
   fetch data, format money, or name database columns are as wrong with
   shadcn as without it. Only the "no library" decision and its corollaries
   are being changed.

## Decision

Adopt shadcn/ui as the primitive layer in `apps/web`, and keep ADR-0013's
pure-presenter rules for everything above it. Components sit in **two
layers** with different rules.

### Layer 1 — primitives: `apps/web/app/components/ui/`

- Generated by the shadcn CLI (`pnpm dlx shadcn@<pinned> add <name>`), one
  component per PR or per screen that needs it. **Only components a screen
  uses are added** — no bulk install.
- shadcn's conventions apply here and only here: a `className` prop merged
  through the `cn()` helper (`apps/web/app/lib/cn.ts`), `cva` variants, and
  `"use client"` where the Radix primitive requires it.
- Once generated, a file is our code. Local edits are allowed, and a re-run
  of `shadcn add` over an edited file is reviewed as a diff like any other
  change.
- `components.json` at `apps/web/` pins the style, the alias paths
  (`@/app/components/ui`, `@/app/lib/cn`), and `rsc: true`, so the CLI's
  output lands where this ADR says.

### Layer 2 — domain components: `apps/web/app/components/`

ADR-0013's rules carry over unchanged:

- **Pure presentation**: no Prisma, `fetch`, `currentUserId()`, or import
  from `@project/domain`, `@project/db`, `@project/services`, or
  `@project/auth`. Imports are React, layer-1 primitives, sibling
  components, and types.
- **Display-ready props**: money and dates arrive pre-formatted as strings;
  `Decimal` is never narrowed to `number` on the way in.
- **Screen-language props**: `BillCard` takes `restaurant`, `total`, not
  column names.
- **No `className` or `variant` prop on a domain component.** Domain
  components may pass `className` and `variant` *down* to primitives; they do
  not accept them *from* screens. The overridable surface ends at layer 1.
- **No client boundary without state**: a domain component is `"use client"`
  only if it owns state, an effect, or a handler itself. Rendering a client
  primitive does not make the parent a client component.

### Rules that span both layers

- **Pages stay server components.** Client boundaries are leaves — a dialog,
  a picker, a form — never a whole `page.tsx`. Data is fetched on the server
  and passed down as display-ready props.
- **Tokens stay in `globals.css` and stay semantic.** shadcn's variable names
  (`--background`, `--foreground`, `--primary`, `--muted-foreground`,
  `--border`, `--ring`, `--destructive`, `--radius`, …) are declared as
  aliases of the existing tokens (`--color-canvas`, `--color-ink`,
  `--color-accent`, `--color-ink-muted`, `--color-line`, `--color-danger`,
  `--radius-card`) and exposed through `@theme inline`. Our tokens remain the
  source of truth; neither layer names a raw palette step.
- **Dark mode keeps following the OS.** The `prefers-color-scheme: dark`
  block redefines the source tokens, and the aliases follow. shadcn's
  `.dark` class variant is not added, so any `dark:` utility in a generated
  file resolves to the OS preference too. Layer-2 components still carry no
  `dark:` utilities.
- **Location is unchanged**: everything stays in `apps/web`; no
  `packages/ui` until a second app needs it. No file in either layer is named
  for a Next convention.
- `CardBody` is retired in favour of shadcn's `CardContent`; `BillCard`
  composes the shadcn `Card` slots.

### Dependencies added

Added to `apps/web` only, each in the PR that first needs it:

| Package | Why |
|---|---|
| `radix-ui` | the accessible behavior under dialogs, popovers, checkboxes, menus |
| `class-variance-authority` | primitive variants (`Button`, `Badge`) |
| `clsx`, `tailwind-merge` | the `cn()` helper that merges `className` safely |
| `lucide-react` | the icon set shadcn components reference |
| `tw-animate-css` | enter/exit animations for dialogs and popovers |
| `sonner` | toasts — only if a screen adopts the `Sonner` component |

## Alternatives considered

- **Keep ADR-0013 and hand-roll accessible widgets.** Rejected: the dialog,
  combobox, and checkbox-group behaviors are exactly the ARIA work ADR-0013
  said not to hand-roll, and the schedule can't absorb it.
- **Radix primitives with our own styling, no shadcn.** Keeps the
  no-`className` rule, but rebuilds the styling shadcn already provides and
  diverges from the designs drawn from it. The gain is a rule, not a feature.
- **A runtime component library (MUI, Chakra, Mantine).** Rejected: each
  brings its own theming system that competes with Tailwind and the token
  file, and its code is not ours to read or edit.
- **A `packages/ui` for the primitives.** Rejected for the reason in
  ADR-0013: one consumer, so the package is pure overhead.

## Consequences

- **Easier**: dialogs, popovers, comboboxes, checkboxes, and menus arrive
  with keyboard and screen-reader behavior from Radix. Screens can be built
  from the team's designs with little custom markup.
- **Easier**: the domain layer keeps every ADR-0013 benefit — a
  `BillCard` still renders in a test from a literal props object, with no
  database or session.
- **Harder**: the app now ships client JavaScript. Each interactive
  primitive is a client island; the bill list stays server-rendered, but
  the split and pick screens carry a bundle. Keeping boundaries at the leaves
  is a review rule, not something the tooling enforces.
- **Harder**: two styling rules now coexist — primitives accept `className`,
  domain components must not. The directory a file sits in decides which
  rule applies, so a primitive must never be added outside `ui/`, and a
  domain component never inside it.
- **Harder**: generated files are vendored code. Upstream fixes don't arrive
  on their own; pulling one means re-running the CLI and reviewing the diff
  against local edits.
- **Harder**: up to seven new dependencies, all in `apps/web`, against a
  codebase that previously had none for UI.
- **Accepted tradeoff**: the token aliases mean two names exist for each
  color (`bg-surface` and `bg-card`). Layer-2 code prefers our names;
  generated layer-1 code keeps shadcn's, so it can be regenerated without
  hand edits.
