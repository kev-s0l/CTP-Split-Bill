# ADR-0015: Per-participant guest links: pick before finalize, read the split after

## Status

Accepted; supersedes [ADR-0012](0012-public-share-link.md)

## Context

ADR-0014 makes Receipt.ownerId the only access boundary and defers public
sharing. The planned flow lets the organizer send each guest a link so the
guest taps the items they had, instead of the organizer assigning everything.
Guests have no accounts, so there is no user to scope by.

ADR-0012 proposed a read-only, party-wide share token so guests could see
what they owe. Parties no longer exist, and a read-only token cannot record
picks. Guests still need to see the final split, and a second link system
for that would duplicate the token model.

Links reach guests from the organizer, not from the app. The organizer sends
each link by text, email, or copy and paste from their own phone. The app
has no SMS or email provider, and adding one brings an API key, per-message
cost, and US carrier registration for application-sent texts.

## Decision

Allow one kind of unauthenticated access: a participant found by its guest
token. The token is the scope; it authorizes exactly one participant on
exactly one receipt. One token serves two phases.

### The token

- Each participant may hold one token: 32 bytes from a CSPRNG,
  base64url-encoded, stored only as a SHA-256 hash in
  participants.pick_token_hash (unique). The raw token is returned once, to
  the owner, when it is issued.
- Only the owner issues, rotates or revokes a token, through owner-scoped
  routes. Rotation and revocation invalidate the old token immediately.
- A token has no expiry. It stops working when it is revoked or rotated,
  when its participant is removed, or when the receipt is deleted.
- Unknown, revoked, rotated, removed-participant and deleted-receipt tokens
  all return the same 404. A receipt that is PARSING also returns that 404.
- Ids are never accepted in place of a token on these routes.

### Before finalize: pick

- A token reads a fixed projection of its receipt: merchant, purchase date,
  currency, items (line number, name, quantity, line total), every
  participant's display name, and which participants picked each item.
- A token writes only its own participant's picks and done flag, only while
  the receipt is DRAFT and not PARSING. Guest writes take the receipt row lock
  but no expectedRevision, because they never overwrite another person's rows.

### After finalize: read the split

- On a FINALIZED receipt the same token is read-only. The projection keeps
  the receipt and item fields above and adds, for every participant, their
  display name, amount owed and settled state, plus the payer's display name.
- Picks and done on a FINALIZED receipt return 409 `CONFLICT`. The holder can
  already see that the receipt is finalized, so the 409 reveals nothing new.

### Never returned, in either phase

- Phones, emails, owner identity, blob names and raw extraction.

### Delivery and link hygiene

- The server sends no messages. Issuing returns `{ url }` once; the owner's
  screen turns it into `sms:` and `mailto:` links pre-filled with the
  participant's stored phone or email, plus a copy action. Sending again
  later means rotating, which invalidates the earlier link.
- Opening a link never changes anything: GET has no side effects, so link
  previews generated by messaging apps are harmless.
- The guest page uses generic page metadata ("Split Bill"), so a link preview
  shows no merchant, names or amounts. It sends `Referrer-Policy: no-referrer`
  and `X-Robots-Tag: noindex`, and logs never record the token, since the
  token travels in the URL path.

## Consequences

- Easier: guests pick and later check what everyone owes without signing up,
  through one link and one route family a reviewer can audit against this
  list. No separate share-link system is built.
- Easier: no messaging provider, keys or per-message cost; delivery works on
  any phone the organizer already has.
- Harder: a forwarded link lets its holder pick for that participant until it
  is rotated. Picks are not attributable beyond "whoever held the token".
- Harder: after finalize, a forwarded or leaked link shows every
  participant's name and amount owed for as long as the link lives. Accepted
  because those are low-sensitivity, rotation and revocation end it, and
  phones and emails never leave owner responses.
- Harder: the organizer must send a link when it is issued, because the raw
  token cannot be read again. Re-sending means rotating.
- Guests picking at once are serialized, not rejected. Each guest write still
  advances the revision, so an owner saving over a pre-pick view gets 409.
- Application-sent SMS or email is a later decision with its own ADR
  (provider, cost, carrier registration).
- On acceptance: docs/specs/api.md and docs/specs/web.md gain a pointer to
  this exception; ADR-0012 is marked superseded; docs/specs/bills/public-share.md
  is retired in favor of docs/specs/receipts/guest-picks.md.
